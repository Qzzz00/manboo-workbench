# 给 Codex 的说明(工作台源码包)

这个包是**工作台本体的源码**。你在这台机器上改它,在这台机器上构建并装上,
改完把改动导出成一个 zip 发回给维护者,由他合并、跑全套测试、发版给所有人。

> 这份说明是给**写代码的那一家**(Codex / Claude Code 之类)看的。
> 四个 `.sh` 脚本是给人双击/粘贴跑的,都不需要先装 git、node 或 pnpm。

---

## 一、第一条规矩:只改这个目录,别碰安装目录

**要改的是**:这个包里的 `源码/workbench-plugin/`(插件源码,TypeScript)。

**绝对不要改**这几处 —— 它们是**构建产物与安装目录**,下一次工作台更新会原样覆盖掉,
在那里改东西等于白改,而且会让这台机器与别人的机器不一样、出了问题谁也查不出来:

| 不要动 | 它是什么 |
|---|---|
| `~/.dsh/profiles/web/node_modules/@ben/dsh-workbench/lib/index.js` | 构建产物(服务端那半) |
| 同上 `lib/client.js` | 构建产物(浏览器里那半) |
| `~/.dsh/runtime/`、`~/.dsh/bin/`、`~/.dsh/packages/` | 工作台的运行环境与安装件 |
| `/Applications/工作台.app` | 外壳 |

把源码改完,跑 `bash 构建并装上.sh` —— 它会构建出新的 `lib/index.js` / `lib/client.js`
并**按工作台自己更新时的同一条路**装进 `~/.dsh/profiles/web`。

## 二、第二条规矩:分清「用户层」和「本体」

工作台分两层,这个包里的源码是**本体**:

- **本体**(这个包):所有人用的是同一份,我们发版、热更新。改它要走「改源码 → 导出 → 维护者合并 → 发版」这条路,**也就是这个包**。
- **用户层**(不在这个包里,全在这台机器上,永远不上传、不合并、本体更新时原地不动):
  - 布局 `~/.dsh/workbench/layout.json`
  - 小组件:运营那六格 `~/.dsh/workbench/用户层/小组件/<格>/`(页内,widget.json + index.js);「开发一个小工具」做的 `~/.dsh/workbench/用户层/网页小组件/<id>/`
  - 偏好 `~/.dsh/workbench/evolve.json` 与工作目录里的 `进化日志.md`
  - 采集器定义 `<工作目录>/采集器/<名>.json`、采回来的数据 `<工作目录>/数据/<名>/`

**先判断一下要做的事落在哪一层。** 如果要的只是「我想在工作台上多看一格数据」、
「把这一格挪到右边」、「照我的口径改一下发布计划那一格」—— 那是**用户层**,
正常的做法是跟事务官说一句(它会派活做一个她自己的小组件),**不用改本体、不用这个包**。

要改本体的,典型是:工作台界面本身的毛病、某个环节的逻辑不对、
电话/手机/展示台那几条链路、设置页、事务官的技能正文。

另外三件事写死在本体里,**任何自我迭代都不许碰**(PRD §9):
AI 悬浮窗、回滚机制、记忆读写规则、日结功能本身、澄清环节。

## 三、目录长什么样

```
工作台源码包-<版本>/
  给Codex的说明.md      ← 你正在读的这份
  构建并装上.sh          ← 改完跑这个
  跑测试.sh              ← 跑测试/类型检查
  导出我的改动.sh        ← 要发给维护者时跑这个
  回滚.sh                ← 装坏了退回去
  包信息.json            ← 这个包是从哪一版、哪个提交打出来的
  基线源码.tgz           ← 打包那一刻的源码快照(**别删**:导出改动要拿它来比)
  node_modules.tgz       ← 预装好的依赖(第一次跑脚本时自动解开;**别删**)
  deepseek-harness/      ← 上游 DSH 的源码子集,**只读参考**,测试解析类型要用
  源码/                  ← 要改的就是这里(摆成仓库根的样子)
    AGENTS.md            ← 仓库的规矩,写代码之前先读
    workbench-plugin/    ← 插件本体
      src/index.ts       ← host 半区(Node 侧:服务、接口、事务官)
      src/client/        ← 浏览器里那半(界面)
      tests/             ← 测试
      docs/              ← 插件自己的文档
    docs/技能/           ← 事务官的技能正文(改了要重新构建才会进插件)
    docs/记忆/           ← 事务官照着做的文档
    .dsh/skills/         ← 事务官自己的技能
    channel-worker/src、butler-app/src、display-client/src   ← 只读参考(接缝对照用)
    deploy/、butler-server/server/                          ← 只读参考,**别跑 deploy 里的脚本**
```

**注意**:整个仓库 300 多 MB,这个包只带了插件和它要用到的那几样。
`relay/`、`phone-bridge/`、`workbench-app/`(外壳)、`installer-app/`、展示台与手机端的资源
都不在包里 —— 要改那些,跟维护者说,不要在这个包里凭空新建。

**`deploy/` 在包里只是给你看的**(有几条测试要读它的形状)。那里面是发版与装机的脚本,
发版只由维护者做 —— **一条都不要跑**。

## 四、怎么改、怎么验

**仓库的规矩先读一遍**:`源码/AGENTS.md` 与 `源码/workbench-plugin/AGENTS.md`。
里面有两条每次都适用:

1. **先写测试再写实现(TDD)**。改完**必须**跑一遍测试与类型检查。
2. 默认简体中文;代码标识、路径、API 字段保留原文。注释只写「现在为什么」。

跑测试:

```bash
bash 跑测试.sh tests/那个文件.test.ts      # 平时就这样:只跑你动过的那部分
bash 跑测试.sh --typecheck                 # 类型检查(tsc --noEmit)
```

想直接用 vitest(效果一样,`跑测试.sh` 就是帮你把 `node` 摆上 PATH):

```bash
cd 源码/workbench-plugin
PATH="$HOME/.dsh/node/bin:$PATH" node_modules/.bin/vitest run tests/那个文件.test.ts
PATH="$HOME/.dsh/node/bin:$PATH" node_modules/.bin/tsc --noEmit
```

**这台机器上没有 `node`、`npm`、`pnpm`、`git` 在 PATH 上,也不用去装。**
工作台自己带了一份 node,在 `~/.dsh/node/bin/`;依赖已经预装在包里,不用联网装。

**全跑(`bash 跑测试.sh` 不带参数)一定会有一批文件红,那不是你改坏的**,三类:

1. **要 `git` 这个命令的**(三十多个文件:建临时仓库当夹具,或者拿它数源码)——
   这台机器上没有它,那些跑不了。
2. **运行时真去 import 上游 DSH 的 client 包的**(`@deepseek-ai/dsh-client-store`、
   `dsh-client-ui-renderer/client`)—— 包里带了上游的源码子集,但带不了整个上游仓库
   (它自己的依赖 1.4GB)。
3. **要读这个包里没带的兄弟目录的**接缝对照用例。

所以:**只跑你动过的那部分**。全套由维护者在他那边跑 —— 你交回去的改动他会重新跑一遍。

改完装上:

```bash
bash 构建并装上.sh
```

它会:构建 → **先把你现在装着的那一份备份到 `~/工作台源码包备份/<时刻>/`** →
按工作台自己更新时的同一条路装进 profile → 核一遍装进去的确实是刚构建的那一份 →
提醒重启工作台。**任何一步失败都会自动把上一版放回去。**

> 这一步**要联网**(它转手给 pnpm,pnpm 要去取这个插件的 peer 依赖;官方源不通会自动换国内镜像)。
> 装完要**把工作台重启一下**(设置 → 重启工作台,或者退出再打开)才看得到。

装坏了:

```bash
bash 回滚.sh --列一下      # 看有哪几份备份
bash 回滚.sh               # 退回最近那一次装之前的样子(不联网)
```

## 五、交付:导出改动发给维护者

做完、测过、在界面上确认过了,跑:

```bash
bash 导出我的改动.sh
```

它和包里自带的 `基线源码.tgz`(打包那一刻的源码)逐文件比,产出
`我的改动-<日期>.zip`,里面是:基线是哪一版哪个提交、改了哪些文件、一份 diff、
以及每个改过/新加的文件的完整新内容。把那个 zip 发给维护者就行(微信、网盘都可以)。

它**不会**把 `node_modules/`、任何叫 `lib/` 的目录(构建产物)、`dist/`、`*.generated.ts`
(从技能文档现算出来的)、`*.tsbuildinfo`、`.DS_Store` 算进改动 —— 那些是机器生成的,
维护者那边重新构建就有。

> 顺带一个后果:`butler-server/server/lib/` 那里面是源码而不是产物,但它也在 `lib` 这一刀里 ——
> 在这个包里改它导不出来。那块本来就只是只读参考,要改跟维护者说。

**这个包里不许放任何凭据**:API Key、密码、Cookie、Token 一律不写进源码、
不写进测试、不写进注释。导出的 zip 会原样发出去。

导出之后你这边的源码一个字没动,可以接着改;下次再导出一次就行。

## 六、容易踩的几个坑

- **改了 `docs/技能/*.md`、`.dsh/skills/*/SKILL.md`、`docs/记忆/下班例程.md` 之后一定要重新构建。**
  它们是构建时打进插件的(`构建并装上.sh` 第一步就在做这件事)。只改文档不构建 = 工作台里还是旧的。
- **不要改 `src/server/bundledSkills.generated.ts`**。它是上面那一步生成的,手改会被覆盖,
  而且有用例逐字比对。
- **不要 bump `workbench-plugin/package.json` 里的 `version`。** 版本号由维护者发版时统一定;
  你改了它,导出的改动落到仓库里会和别的卡打起来。
- **不要新建数据库、后台扫描器、路由器**(仓库 YAGNI 那一条)。
- **不要往 `源码/` 里塞 `.git`**,也不要指望这里能跑 git —— 这台机器上没有 git,
  版本管理由维护者那边做,你只要改文件。
- **改了接缝(8791 接口、房间协议、中转接口、壳的操作、家族目录)要说一句**:
  在你给人的交代里写清碰了哪一条、还有哪几条兄弟路没查 —— 维护者合并时要照这个核。
