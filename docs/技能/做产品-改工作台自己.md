# 技能:做产品 - 改工作台自己

> 这份是**事务官的技能**。工作台会把它整段写进 `~/.dsh/AGENTS.md` 的
> `<!-- 引导:做产品-改工作台自己:开始 -->` … `<!-- 引导:做产品-改工作台自己:结束 -->` 标记段里,
> 段外一个字不动。**只有「做产品」模板下写** —— 运营模板下的事务官不需要知道有这条路。

## 什么时候算「改自己」

一条需求卡,它挂的那个项目**就是工作台自己的仓库**。判据只有两条,而且**不由我判断**
—— 工作台已经替我判过了,我从 `POST /feature/docs` 回的 `self` 那一格读结论:

1. 项目根有 `deploy/publish-update.sh`;
2. `workbench-plugin/package.json` 里的包名是 `@ben/dsh-workbench`。

`self` 是 `false` 时,这条需求按普通需求卡办(梳理 → 拆解与派活 → 验收 → 记录),
**底下这一整套一步都不做**:别人的仓库没有发版链,也没有一个跑着的工作台等着热更新。

## 先记住的一条:不在他正用着的那份仓库里改(2026-09-25)

项目根(= 他正开着、正在用的那份 checkout)**不是我的工作台**。在那里 `git checkout -b`、改文件,会把他那份仓库换到别的分支上
(09-25 真出过一次:统筹紧接着往 main 提交的东西落到了我那条分支上)。所以:

- 任何「改自己」的活,**先开独立工作区**(下面第一步 `POST /feature/branch`),子事项都在那个 worktree 里做;
- 写代码的活**派给写代码的那家**(`POST /dispatch/run`,`kind: "code"`):工作台会在这件事的独立工作区里跑它,不在项目根;
- 合并与发布只走 `POST /feature/ship` 那固定的八步(看得见、每步失败就停、撤得回);
- 工作台会**拦下**在项目根里 `git checkout / switch / reset / commit / merge …` 和往里写文件的工具调用,拦下时那句话会说去哪做。
- **2026-09-28 起这道门更宽了**(卡 BS2、设计第五节第 1 道门):**凡 git 仓库我一律只读** —— 独立工作区也一样,
  他自己的项目也一样;**构建 / 测试 / 装依赖的命令(`pnpm`、`npm`、`vitest`、`tsc`、`make`、`swift build`、`xcodebuild`…)一律拦**。
  这不是要绕的东西:**这是派出去的活**。撞上了就照拦下那句话去 `POST /dispatch/run`(`kind: "code"`),
  或者请他挑一家 / 先把那一家接上;**不要重试、不要换个写法再来一次**。
  全量测试那一步在下面 `/feature/ship` 的八步里,是**工作台自己跑**的,不用我跑。
- **底下每一条 POST 都带身份头**(2026-09-28,A11):`-H "x-workbench-actor: $WORKBENCH_BUTLER_ACTOR"`。
  `/feature/branch`、`/feature/result`、`/feature/docs`、`/feature/confirm` 改的都是这张卡摆出来的状态,
  没带会回 403;那个值在我自己的环境变量里。**`/feature/ship` 那一下例外:它只有他本人按得下,
  我带着令牌照样被拒 —— 被拒了不要绕、不要重试,把这一版准备好然后叫他来按。**

## 每一步我做什么

### 一、「拆解与派活」这一态,**派活之前先开分支**

```
POST /feature/branch { id: "<卡 id>" }
```

它在项目根开 `feat/<需求名-slug>`,并把 worktree 开在 `.claude/worktrees/<slug>`。
回的 `worktree` 就是**接下来每一件子事项的工作目录** ——
派给 Codex 的那条命令,`-C` 后面写的是它,不是项目根。

**不在 main 那份 checkout 上改**。main 那一份是合并与发版用的;在上面直接改,
一次没收干净的改动就会跟着下一次发版走出去。

分支已经开过了它会照样回成功(`created:false`),所以这一步**可以放心重来**。

### 二、每件子事项跑完,**把结果报回卡上**

那条命令跑完之后(不管成没成),立刻:

```
POST /feature/result {
  id: "<卡 id>",
  item: "<子事项的名字>",
  exit_code: <退出码>,
  log: "<原始输出,不用我摘要>",
  hand: "Codex",              // 派给了谁
  cwd: "<那条命令跑在哪个目录>"   // 必须在这个项目里
}
```

**我只报两样我手上才有的东西:退出码与原始输出。**
「改了哪些文件」(`git status --short` + `git diff --stat`)与「测试跑没跑」
由工作台自己去问 —— 我不转述,也不替它们写摘要。

它会落一份 `docs/需求/<需求名>/结果-<子事项>.md`,卡上「验收」页签念的就是它。

**退出码不许编。** 不知道退出码就不发这一条:一句"看起来成了"比没有结果更坏。

截图这一项:这台机器上**没有**现成的截屏能力(`screencapture` 要屏幕录制授权,
只有 维护者 能给;而客户端窗口的截图会把他的私人对话一起拍进仓库)。
工作台会在结果文件里如实写「没截」并写清为什么,**我不要去想办法截**。

### 三、「验收」态他点「通过」之后,那条闭环

**这一下不是我按的**(2026-09-28 维护者拍板)。`/feature/ship` 只有**他本人**按得动 ——
电脑上点、手机上点。我打这条口会被回 403,回的那句话就是这个意思,**不要绕、不要重试**。
我该做的是把这一版准备好(产物、把关、决策记录都齐了),然后叫他来按(卡上「通过」那一下,
或者按「跟进与收回」那一节打一通电话)。同一条规矩下的另外三个口:`/approvals/answer`、
`/questions/answer`、`/asks/voice` —— 「等你确认」里的每一条都只有他能答,我替他答不了,
**也不要替他编一个答案往下走**。

```
POST /feature/ship { id: "<卡 id>" }        // 他按的那一下走这条;我不发它
```

工作台**按顺序**做这八步,每一步失败就停:

| | 这一步 | 做什么 |
|---|---|---|
| ① | 过一遍不许改的东西 | 分支上改过的文件挨个过硬边界 |
| ② | 全量测试 | `workbench-plugin` 的 `pnpm typecheck && pnpm vitest run`;改到 butler-app / channel-worker / butler-server 就各跑各的 |
| ③ | 合并 | `git merge --ff-only` —— **不能快进就停下叫人** |
| ④ | 版本号 | `npm version patch --no-git-tag-version`,发版记录第 7 行插一行(人话) |
| ⑤ | 提交 | `git add` 那两个文件 → commit(署名尾行写这条 DSH 会话)→ push |
| ⑥ | 发版 | `bash deploy/publish-update.sh --with <按改到的包> --notes "<人话>"` |
| ⑦ | 记录 | 决策记录追加一条、`docs/进化日志.md` 留一条,状态如实写「待重启确认」 |
| ⑧ | 热更新 | `POST /update/apply`,**按下就回**(不等版本号) |

★ **记录在热更新之前,而且更新那一步不等**(2026-09-23 定的)。理由:`/update/apply`
会把跑着这条请求的那个工作台进程换掉并重启 —— 记录留到那之后就永远写不成了,
而一次没有记录的自我修改是这条路上最不该发生的事。

代价是回包那一刻还不知道这一版生没生效。所以 `/feature/ship` 成了的时候回的是
`{ ok:true, note:'已触发热更新,重启后见' }`,进化日志那一条标着「待重启确认」。
**那不是敷衍,是实情。** 工作台重启起来之后会自己对一次版本号,
对上了把那一条改成「已生效」并在收件箱里说一句,对不上也在收件箱里说一句。

**这八步我一步都不自己跑。** 我发的是那一条 `POST /feature/ship`,其余由工作台做 ——
它做得到的事我去手跑一遍,等于同一件事有两条路,而那两条路迟早会说两个版本的话。

跑完之后卡会自己推到「记录」态。我在那一态把 `记录.md` 的四行写出来
(需求 / 做了什么 / 谁做的 / 遗留),她点一下「写进决策记录」就收尾。

## 什么情况停

**每一步失败就停,不自动重试。**

`/feature/ship` 回 `{ ok:false, stopped_at, note }` 时,`note` 是那一步失败的**原话**。
这时候:

- 卡已经挂成「阻塞 · 出错」,收件箱里已经有一条带原话的,座机也已经排了一通 —— **这三样都不用我做**;
- 我要做的只有一件:**在会话里把那句原话原样说给他听**,并说清停在第几步;
- **不要再点一次 `/feature/ship`**。要再来一次是他的决定,那一次得有人看着。

三种最常见的停法,以及各自该说的话:

1. **测试红**(停在 ②):把 `note` 里那段测试输出原样贴出来。这条不用叫人来修环境 —— 是代码红了;
2. **合并冲突 / 快进不动**(停在 ③):main 上有分支没有的提交。
   **我不 rebase、不 merge、不 force** —— 这一条只有人能定怎么办;
3. **发版失败**(停在 ⑥):main 上已经有那一笔了(版本号也已经 +1),`note` 里会写清楚。
   这一步没成,记录与热更新都不会发生;
4. **更新作业起不来**(停在 ⑧):**发版是成的**,记录也已经落了(标着「待重启确认」),
   只差这台电脑没换过来 —— 让他去设置里点一次「检查更新」。

另外一种不是"停",但要跟他说清楚:`/feature/ship` 回 `{ ok:true }` **不等于这一版
已经在他电脑上跑起来了**,只等于"更新按下去了"。真结果在工作台重启之后的收件箱里。

## 我不许碰的东西

工作台在第 ① 步会拿分支上改过的文件挨个过一遍,撞上就**不合**。这不是建议,是一道门:

- `deploy/` —— 发版链本身。改自己的那条路不能顺手改开门的那把锁;
- `.claude/` —— 会话与 worktree 的家当;
- `docs/交接-*` —— 交接是人写给人的过程记录。**能改的那一份 docs 只有 `docs/发版记录.md`**,
  而那一行由工作台自己插,不用我写;
- `~/.dsh` 底下任何东西 —— 那是这台机器上跑着的那一份,不是仓库;
- 仓库外面的任何路径。

所以**派活的时候就要把这几条交代给 Codex**:让它只改 `workbench-plugin/`、
`butler-app/`、`channel-worker/`、`butler-server/` 里该改的那几个文件。
撞了边界不是"稍后再修"——是整条闭环当场停在第一步,这一版发不出去。
